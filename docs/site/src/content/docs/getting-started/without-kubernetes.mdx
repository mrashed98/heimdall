Heimdall is one binary and a Postgres database, so it runs anywhere Linux and
Postgres do. This page covers two ways: Docker Compose on one host, and the
release binary as a systemd service. Both use the same `heimdall.yaml` as the
[Helm chart](/heimdall/getting-started/kubernetes/).

## What changes outside Kubernetes

Everything works the same except reading a cluster:

- **No cluster inventory.** Sight, which lists pods, nodes, Helm releases and
  ArgoCD Applications, needs a cluster. Without one, Heimdall logs `no cluster
  client` at startup and skips it. If you also run a cluster elsewhere, run
  `heimdall sight --realm <realm> --push <this server's URL>` there (with
  `HEIMDALL_API_KEY` set) and it sends that cluster's inventory here.
- **Docker hosts instead.** [Sight for Docker](#sight-for-docker) reads the
  containers a Docker host runs, including the one Heimdall itself runs on.
- **What you run comes from:**
  - SBOMs uploaded from CI, by [`heimdall gate`](/heimdall/guides/ci-gate/) or
    by `POST /api/v1/ingest/sbom` (see the
    [HTTP API](/heimdall/reference/http-api/#post-apiv1ingestsbom)). Generate
    one for a server or an image with `syft <image or dir> -o cyclonedx-json`.
  - Components you list under
    [`declared`](/heimdall/reference/configuration/#declared), such as a
    database on a VM.
  - The release watchers in
    [`watchers`](/heimdall/reference/configuration/#watchers), which need no
    inventory at all.
- **No image scanner job.** `heimdall scan-images` scans the images Sight
  found. Without a cluster it only has work when [Sight for
  Docker](#sight-for-docker) is on; otherwise upload image SBOMs from CI.

Alerts, the web console, oaths, the CI gate and the API are unchanged.

## Sight for Docker

Sight for Docker lists a Docker host's running containers and reports them
like Sight reports a cluster:

- Each container is a service named `<host>/<name>`. The name is the
  container's `heimdall.service` label, else `<project>-<service>` from its
  Compose labels, else the container name. `<host>` is the name Docker
  reports, or `sight.docker.name` / `--docker-name`.
- Its image is a component, so its advisories and new releases are found
  like a pod's. An image pulled from a registry (it has a registry digest)
  is also queued for the SBOM scanner; a locally built one is not.
- The host's OS (Ubuntu or Debian) is a component of the service `<host>`.

A host is identified by its Docker engine ID, not its name. A scan replaces
that daemon's services only, so a realm can hold a cluster and any number of
Docker hosts, and renaming a host empties its services under the old name.
A service name another source already holds (the cluster, or another host
with the same hostname) is skipped and logged, not taken over: give hosts
that share a hostname their own `name`. Heimdall only reads from Docker
(`GET /info`, `/containers/json` and `/images/{id}/json`). With
`sight.docker` set, the Overview's feed health shows **Sight for Docker**
with the server's own last successful scan; scans pushed from other hosts
with `--push` don't update it.

<Aside type="caution" title="The Docker socket">
Access to the Docker socket is root on the host. Give Heimdall a read-only
socket proxy rather than the socket itself.
</Aside>

With the Compose install, add a socket proxy next to Heimdall:

```yaml
services:
  docker-proxy:
    image: tecnativa/docker-socket-proxy
    restart: unless-stopped
    environment:
      INFO: 1
      CONTAINERS: 1
      IMAGES: 1
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
```

and point Heimdall at it in `heimdall.yaml`:

```yaml
sight:
  docker:
    host: tcp://docker-proxy:2375
    name: vm1        # optional; default: the name Docker reports
```

It runs at startup and then every `schedules.sight_minutes` (15 by
default). To report other Docker hosts to this server, run this on each
of them (from cron or a systemd timer), with `HEIMDALL_API_KEY` set to an
ingest key:

```bash
heimdall sight --docker --realm prod --push https://heimdall.example.com
```

The images it finds can be scanned for SBOMs with `heimdall scan-images`, on
a schedule of your choice. It needs `syft`, access to the registries, and
`HEIMDALL_URL` and `HEIMDALL_API_KEY` (an ingest key), like the CLI.

## Docker Compose

The compose file runs Heimdall and Postgres 17 on one host. It is in the
repository at `deploy/compose/` and needs Docker Compose 2.24 or later
(`docker compose version`).

<Steps>

1. Get the compose file and the example environment:

   ```bash
   mkdir heimdall && cd heimdall
   curl -fsSLO https://raw.githubusercontent.com/mrashed98/heimdall/main/deploy/compose/docker-compose.yml
   curl -fsSL -o .env https://raw.githubusercontent.com/mrashed98/heimdall/main/deploy/compose/.env.example
   ```

2. Fill in `.env`. Each line says how to generate its value:

   ```bash
   cat > .env <<EOF
   POSTGRES_PASSWORD=$(openssl rand -hex 24)
   HEIMDALL_BOOTSTRAP_ADMIN_KEY=hd_$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=')
   HEIMDALL_SECRET_KEY=$(openssl rand -base64 32)
   EOF
   ```

   All three are required; `docker compose up` names any that is missing.
   Use only URL-safe characters in `POSTGRES_PASSWORD`, since it goes into the
   database URL as is. Keep a copy of `HEIMDALL_SECRET_KEY`: without it,
   secrets saved in the console cannot be read back.

3. Write `heimdall.yaml` next to the compose file. The smallest one names
   your realms:

   ```yaml
   realms: [prod]
   ```

   See the [configuration reference](/heimdall/reference/configuration/) for
   channels, watchers and declared components. If it names environment
   variables (`webhook_env: SLACK_WEBHOOK`), put them in `channels.env`
   beside it; the compose file loads that file when it exists.

4. Start it:

   ```bash
   docker compose up -d
   curl -s localhost:8080/healthz    # 200 once Postgres is reachable
   ```

5. Open `http://localhost:8080` and sign in with the bootstrap key, or set
   up [local accounts or OIDC](/heimdall/guides/sign-in-access-control/).

</Steps>

The port is bound to `127.0.0.1`. To reach the console from other machines,
put a reverse proxy with TLS in front of it, or change the port line to
`"8080:8080"` on a network you trust. To upgrade, set `HEIMDALL_VERSION` in
`.env` to the release number, without the `v`, and run `docker compose up -d` again; Heimdall
applies its database migrations at startup. Back up the `postgres` volume as
you would any database.

## Binary and systemd

Each release has static Linux binaries for amd64 and arm64
(`heimdall-linux-amd64`, `heimdall-linux-arm64`) with the web console built
in. You need a Postgres database Heimdall can reach (CI tests against
Postgres 17); it creates its own tables.

<Steps>

1. Download the binary, check it, and install it:

   ```bash
   ARCH=amd64   # or arm64
   BASE=https://github.com/mrashed98/heimdall/releases/latest/download
   curl -fsSLO "$BASE/heimdall-linux-$ARCH"
   curl -fsSLO "$BASE/SHA256SUMS"
   sha256sum --check --ignore-missing SHA256SUMS
   sudo install -m 755 "heimdall-linux-$ARCH" /usr/local/bin/heimdall
   ```

   `SHA256SUMS` is published with every release after 0.3.2. For 0.3.2 and
   earlier, compare against the checksum shown on the release page instead.

2. Write the config and the environment file:

   ```bash
   sudo mkdir -p /etc/heimdall
   sudo tee /etc/heimdall/heimdall.yaml >/dev/null <<'EOF'
   realms: [prod]
   EOF
   ADMIN_KEY="hd_$(openssl rand -base64 32 | tr '+/' '-_' | tr -d '=')"
   sudo tee /etc/heimdall/heimdall.env >/dev/null <<EOF
   DATABASE_URL=postgres://heimdall:CHANGE_ME@localhost:5432/heimdall
   HEIMDALL_BOOTSTRAP_ADMIN_KEY=$ADMIN_KEY
   HEIMDALL_SECRET_KEY=$(openssl rand -base64 32)
   EOF
   sudo chmod 600 /etc/heimdall/heimdall.env
   echo "Admin key: $ADMIN_KEY"   # sign in with this; it is also in the file
   heimdall serve --check-config /etc/heimdall/heimdall.yaml   # prints "config ok"
   ```

   Replace `CHANGE_ME` in `/etc/heimdall/heimdall.env` with the database
   password (URL-safe characters, or percent-encode the others).

3. Install the service. The unit in the repository at
   `deploy/systemd/heimdall.service` runs Heimdall as a dynamic user with
   1 GB of memory and one CPU at most, and a read-only view of the system:

   ```bash
   sudo curl -fsSL -o /etc/systemd/system/heimdall.service \
     https://raw.githubusercontent.com/mrashed98/heimdall/main/deploy/systemd/heimdall.service
   sudo systemctl daemon-reload
   sudo systemctl enable --now heimdall
   curl -s localhost:8080/healthz
   journalctl -u heimdall -f
   ```

</Steps>

Heimdall listens on port 8080 on every interface. Use a firewall or a reverse
proxy with TLS to control who reaches it.

<Aside type="note">
Heimdall needs outbound HTTPS to OSV, NVD, the EPSS feed, GitHub and the
other registries it watches, and to your alert channels. It never needs
inbound access from the internet.
</Aside>
