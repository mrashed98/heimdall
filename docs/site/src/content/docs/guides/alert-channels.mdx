Gjallarhorn can announce findings on several channels at once. Each entry under
`channels:` has a `type`, a unique `name`, the `realms` it covers (empty = all)
and a `min_severity`. Routing and the immediate-versus-digest rules are the
same for every type (see [Alert rules](/heimdall/concepts/alerts/)); only the
message format and the delivery differ.

```yaml
realms: [prod, dev]
channels:
  - type: slack
    name: dev-chat
    webhook_env: SLACK_WEBHOOK_DEV
    realms: [dev]
    min_severity: high
  - type: pagerduty
    name: oncall
    routing_key_env: PAGERDUTY_ROUTING_KEY
    realms: [prod]
    min_severity: critical
  - type: email
    name: security-team
    host: smtp.example.com
    from: Heimdall <heimdall@example.com>
    to: [security@example.com]
    username_env: SMTP_USERNAME
    password_env: SMTP_PASSWORD
    min_severity: high
```

<Aside type="danger" title="Secrets only through *_env keys">
Webhook URLs, tokens, routing keys and passwords never go in `heimdall.yaml`.
Each `*_env` key holds the **name** of an environment variable; in Kubernetes,
put the values in the Secret named by `existingSecret`. Heimdall reads them when
it sends, never stores them in the database, and keeps them out of its logs.
Channels added in the web console are the exception: their secrets are stored
encrypted in Postgres (see [Managing channels in the
console](#managing-channels-in-the-console)).
</Aside>

## Shared behaviour

- **One alert per advisory or release per channel.** A channel only sees the
  findings of the realms it covers, and only when the alert reaches its
  `min_severity` (releases, end of support and Kubernetes CVEs count as `high`).
- **The existing `teams:` list keeps working.** Its routes are Teams channels;
  `teams:` and `channels:` can be used together, and names must be unique across
  both. `type: teams` under `channels:` is the same thing.
- **A realm is covered** when any Teams route or channel covers it. Findings of
  an uncovered realm stay pending (one warning in the logs) and go out once a
  channel covers the realm.
- **The weekly digest and the first-run summary** go to every channel covering
  the realm whose `digest` is on, whatever its `min_severity`. `digest`
  defaults to `true`, except for the paging types (`pagerduty`,
  `alertmanager`), where a weekly summary would page someone; set
  `digest: true` there to opt in, or `digest: false` on any channel to opt out.
  Medium and low findings of a realm that no digest channel covers stay
  pending until one does.
- **Links:** only links Heimdall makes itself (the advisory, the release notes)
  are clickable. Text that comes from upstream, such as release-note lines in
  the digest, is always shown as escaped plain text, so a Markdown link in it
  never becomes a link in any channel.
- **Delivery** goes through the database outbox: about one message every 2
  seconds, retries with a growing delay (30 s doubling to 1 h), `Retry-After`
  honoured (clamped to 1 h), exactly once even across restarts. A message the
  channel rejects (a 4xx other than 429, a permanent SMTP error) is not retried
  and counts in `heimdall_notify_failures_total{channel_type}`.
- **Destinations are checked** before every send: see
  [Where channels may send](#where-channels-may-send).
- **A missing variable** keeps that channel's messages queued until it is set.
  Renaming a channel to another `type` leaves messages queued for the old type
  where they are, rather than sending them in the wrong format.

Every type accepts `name`, `type`, `realms`, `min_severity` and `digest`. Unknown keys are
an error, so a key of another type (say `chat_id` on Slack) is caught at
startup.

## Microsoft Teams

`type: teams`, `webhook_env`. Adaptive Cards through a Workflows webhook; see
[Microsoft Teams alerts](/heimdall/guides/teams/) for setting up the webhook.

## Slack

`type: slack`, `webhook_env` (an [incoming
webhook](https://api.slack.com/messaging/webhooks) URL). Messages use Block Kit:
a header, the severity and realm, the findings, and buttons for the advisory and
release notes.

```yaml
- type: slack
  name: team
  webhook_env: SLACK_WEBHOOK_TEAM
  min_severity: high
```

## Discord

`type: discord`, `webhook_env` (a channel webhook URL: *Channel settings →
Integrations → Webhooks*). One embed per message, coloured by severity. Text is
Markdown-escaped and mentions are disabled, so an advisory saying `@everyone`
pings nobody.

## Telegram

`type: telegram`, `bot_token_env` (a [bot](https://core.telegram.org/bots#how-do-i-create-a-bot)
token from BotFather), `chat_id` (a number such as `-1001234567890`, or
`@channelname`), and optionally `api_url` (default `https://api.telegram.org`,
for a Bot API proxy). Messages use HTML parse mode with every piece of text
escaped. The token sits in the request path, so Heimdall redacts it from every
error it logs.

```yaml
- type: telegram
  name: ops-chat
  bot_token_env: TELEGRAM_BOT_TOKEN
  chat_id: -1001234567890
  min_severity: high
```

## PagerDuty

`type: pagerduty`, `routing_key_env` (the integration key of an Events API v2
integration), optionally `url` (default
`https://events.pagerduty.com/v2/enqueue`; use
`https://events.eu.pagerduty.com/v2/enqueue` for EU accounts). Each alert is a
`trigger` event whose `dedup_key` is the alert's key (`alert|vuln|GHSA-…`), so a
later alert for the same advisory joins the open incident. Severity maps
critical → `critical`, high → `error`, medium → `warning`, the rest → `info`.
Heimdall does not send `resolve` events.

## Prometheus Alertmanager

`type: alertmanager`, `url` (the base URL; alerts are POSTed to
`{url}/api/v2/alerts`), optional basic auth (`username_env` and `password_env`)
or bearer token (`bearer_token_env`), and `expire_after_hours` (default 24).

Each **finding** becomes one Alertmanager alert, so you can route, group and
silence on its labels:

| Label | Value |
|---|---|
| `alertname` | `Heimdall` + kind: `HeimdallVuln`, `HeimdallFixAvailable`, `HeimdallMajorRelease`, `HeimdallOathExpired`, `HeimdallEol`, `HeimdallK8sCve`, `HeimdallReleaseNoteCve` (and `HeimdallFirstRun`, `HeimdallDigest` when the channel sets `digest: true`) |
| `realm` | The finding's realm |
| `service` | The service, when the finding has one |
| `kind` | `vuln`, `fixavailable`, `majorrelease`, ... |
| `severity` | `critical`, `high`, `medium`, `low`, `unknown`; `info` for the digest and summary |
| `advisory` | The advisory id, for advisory kinds |

Annotations: `summary` (the title), `description` (the finding's facts) and
`links` (one URL per line); `generatorURL` is the advisory or release notes.

<Aside title="Resolve policy: fire once, expire">
Heimdall announces a finding once and does not follow it afterwards, so it
never sends a resolution. Each alert is sent once with `startsAt` = the delivery
time and `endsAt` = the delivery time + `expire_after_hours`; Alertmanager shows
it as firing for that long and then expires it. The times are set when the
alert is sent, not when it is queued, so a delayed delivery does not arrive
already expired. If your receivers have `send_resolved: true`, the expiry
produces a "resolved" notification that only means the window ended; consider
`send_resolved: false` on Heimdall's route.
</Aside>

```yaml
- type: alertmanager
  name: am
  url: http://alertmanager.monitoring:9093
  expire_after_hours: 24
  min_severity: high
```

## Generic webhook

`type: webhook`, `url_env` (the URL to POST to) and optionally `secret_env`.
The body is the neutral alert model as JSON:

```json
{
  "version": 1,
  "alert": {
    "key": "alert|vuln|GHSA-gin-0001",
    "kind": "vuln",
    "title": "⚠ GHSA-gin-0001 (high) affects 2 service(s)",
    "severity": "high",
    "realm": null,
    "advisory": "GHSA-gin-0001",
    "summary": "gin mishandles header parsing",
    "scores": "OSV 7.5 · NVD 9.8",
    "notes": [],
    "facts": [],
    "entries": [
      {"finding_id": 1, "realm": "prod", "service": "api", "severity": "high",
       "facts": [{"title": "Component", "value": "pkg:golang/github.com/gin-gonic/gin@v1.9.0"}]}
    ],
    "sections": [],
    "links": [{"title": "Open GHSA-gin-0001", "url": "https://osv.dev/vulnerability/GHSA-gin-0001"}]
  }
}
```

`kind` is a finding kind, `firstrun` or `digest`. Each section line is
`{"link": {"title", "url"} | null, "text": "..."}`: `link` is a link Heimdall
made (a release's notes), `text` may come from upstream and should be shown as
plain text.

Every request carries `X-Heimdall-Timestamp` (Unix seconds, the send time).
With `secret_env`, it also carries `X-Heimdall-Signature: sha256=<hex>`: the
HMAC-SHA256, keyed with the secret, of the timestamp, a dot and the raw request
body (`"{timestamp}.{body}"`). Verify it over the bytes you received, before
parsing, with a constant-time comparison, and reject requests whose timestamp
is more than 5 minutes off, so a captured request cannot be replayed later:

```python
import hashlib, hmac, time

def verify(secret: bytes, headers, body: bytes, tolerance: int = 300) -> bool:
    ts = headers.get("X-Heimdall-Timestamp", "")
    if not ts.isdigit() or abs(time.time() - int(ts)) > tolerance:
        return False
    signed = ts.encode() + b"." + body
    expected = "sha256=" + hmac.new(secret, signed, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, headers.get("X-Heimdall-Signature", ""))
```

A message may be delivered again only if your endpoint answered with an error;
use `alert.key` to drop duplicates.

## Email

`type: email` sends through an SMTP server, in plain text and simple HTML.

| Key | Meaning |
|---|---|
| `host` | SMTP server. |
| `port` | Default by `security`: 587, 465 or 25. |
| `security` | `starttls` (default; STARTTLS is required, never opportunistic), `tls` (implicit TLS) or `none` (only for a relay on a trusted network). |
| `username_env`, `password_env` | Variables holding the SMTP login (set both or neither). Not allowed with `security: none`, which would send the password in clear text. |
| `from` | Sender, `Name <address>` or `address`. |
| `to` | Recipients (at least one). |

```yaml
- type: email
  name: security-team
  host: smtp.example.com
  security: starttls
  username_env: SMTP_USERNAME
  password_env: SMTP_PASSWORD
  from: Heimdall <heimdall@example.com>
  to: [security@example.com, oncall@example.com]
  min_severity: high
```

A temporary failure (a 4xx reply, a network or TLS error) is retried; a
permanent one (a 5xx reply such as an unknown recipient) is not. A failed login
(530, 534, 535) is a problem with the channel, not the message: the whole
channel's queue waits and retries with the usual backoff, so a wrong password
delays mail but never discards it. Fix the credentials and the backlog goes out.

## Managing channels in the console

Admins can also see and manage channels in the web console, under
**Settings → Alert channels**. The list shows every channel, from
`heimdall.yaml` and from the console, with its type, realms, minimum severity,
digest setting and delivery health (queued alerts, the last delivery, and the
error when the queue is failing).

- **Config channels** carry a `config` badge and are read-only: the file stays
  their source of truth. A variable they need that is not set is listed by name,
  never by value.
- **Console channels** have the same types, fields and validation rules as the
  config. **Add channel** opens a form for the chosen type; **Edit** and
  **Delete** (in the ⋯ menu) are on console rows only. A saved channel takes
  part in alerts, the weekly digest and the first-run summary straight away,
  with no restart.
- **Test** sends a fixed test alert to any channel at once, outside the outbox,
  and shows whether it arrived (the error, with secrets redacted, if not). One
  test per channel every 10 seconds.
- Every create, edit, delete and test is written to the audit log
  (`channel_created`, `channel_updated`, `channel_deleted`, `channel_tested`),
  with the channel's name, type and the names of the changed fields, never their
  values.

### The secret key

Secrets entered in the console (webhook URLs, tokens, routing keys, passwords)
are encrypted with AES-256-GCM under `HEIMDALL_SECRET_KEY` before they are
stored in Postgres. The key is 32 random bytes in standard base64:

```bash
openssl rand -base64 32
```

Add it to the Secret named by the chart's `existingSecret` (there is no
separate Helm value), then restart the pod, because the key is read at startup:

```bash
# Use your release's namespace, its existingSecret name and its deployment name.
NS=heimdall SECRET=heimdall-secrets DEPLOY=heimdall
kubectl -n "$NS" patch secret "$SECRET" --type merge \
  -p "{\"stringData\":{\"HEIMDALL_SECRET_KEY\":\"$(openssl rand -base64 32)\"}}"
kubectl -n "$NS" rollout restart deployment "$DEPLOY"
```

Outside Kubernetes, set `HEIMDALL_SECRET_KEY` in the server's environment.

<Aside type="caution" title="Back the key up">
Keep a copy of the key wherever you keep your other secrets, apart from the
database backups. Without it, the secrets stored in the console cannot be
decrypted and every one of them has to be entered again. Changing the key has
the same effect: Heimdall has no key rotation.
</Aside>

**Without the key** (not set, or malformed: not base64 or not 32 bytes, which
logs an error without the value), Heimdall still starts and the config channels
deliver as usual. Management in the console is off: the page lists the
channels and shows a notice instead of **Add channel**, and creating or editing
a console channel is refused. Testing is refused for a console channel whose
saved secrets can't be read. Existing console channels that hold a
secret show **Key missing** and their alerts stay queued until the key is set;
nothing is lost. A console channel with no secret at all (Alertmanager without
authentication, email without a login) keeps delivering. Deleting a channel
works without the key.

**With a different key** than the one the secrets were saved under, the
affected channels show **Secret unreadable: re-enter it** and a warning is
logged once per channel. Their alerts stay queued; other channels are not
affected. To repair a channel, edit it and **Replace** every saved secret, or
**Remove** the optional ones you no longer need. The save is refused until each
stored secret is re-entered or removed; the channel is then encrypted again
under the current key and its queue drains.

**A console channel that no longer passes validation**, for example after an
upgrade tightens a rule, shows **Invalid: see the server log**. The log line
"alert channel `X` from the UI is skipped" gives the reason. Alerts raised while
it is invalid are not queued for it and are not sent to it later; alerts it had
already queued stay queued, and until it is fixed they also trigger the
"no longer configured" warning described in [Orphaned
messages](#orphaned-messages). Edit the channel to fix it, or delete it.

### Secrets

A saved secret is never shown again, in the console, the API, the logs or the
audit log. The form shows it as `•••••••• Saved` with **Replace**, and
**Remove** for optional secrets. A field you leave alone keeps the stored value.
For Teams, Slack, Discord and the generic webhook, **the URL is the secret**, so
it is masked too. The generic webhook's signing secret has a **Generate** button
that fills in 32 random bytes in hex: copy it into the receiving system before
you save, because it cannot be read back afterwards.

### Names and types

- A console channel's name must not contain `:` or control characters, nor
  start or end with a space, and must not be used by any other channel, from the
  config or the console.
- **Name and type cannot be changed** after the channel is created, because the
  outbox keys queued alerts by name and type. To rename, create a new channel
  and delete the old one.
- **The config wins a name clash.** If `heimdall.yaml` later gains a channel
  with the name of a console channel, the config one is used. The console
  channel is skipped from delivery, listed with **Name clash with config: delete
  this channel**, and a warning is logged; Heimdall still starts. Delete the
  console channel. If both have the same type, the alerts queued under that name
  belong to the config channel, and deleting the console channel leaves them
  alone.
- **A realm removed from the config** is dropped from a console channel's
  delivery, with a warning in the logs; the channel keeps covering its other
  realms. The list still shows the realms as saved, so edit the channel to tidy
  them up.

### Deleting a channel

**Deleting a console channel discards the alerts queued for it**, in the same
step: they are marked failed with the reason "channel deleted", so a later
channel with the same name and type never sends them somewhere else. The
confirmation says how many will be discarded. The exception is a name clash with
a config channel of the same type, described above: those queued alerts are the
config channel's and are kept.

**Creating a console channel discards any undelivered alerts still queued under
the same name and type**, for example those of a removed config channel or ones
queued while an earlier channel of that name was being deleted. They are marked
failed with the reason "channel recreated", so a new channel never sends old
alerts to its new destination. The `channel_created` audit entry records how
many were discarded.

## Where channels may send

Before each send, Heimdall looks up the channel's host and connects only to
the addresses it checked, so the check and the connection always agree.

- **Never sent to, by any channel:** link-local addresses (`169.254.0.0/16`,
  `fe80::/10`), which include the cloud metadata service at
  `169.254.169.254` on AWS, Google Cloud, Azure and OpenStack; Alibaba
  Cloud's `100.100.100.200`; AWS's IPv6 `fd00:ec2::254`; and unspecified,
  multicast and broadcast addresses. No alert destination lives there.
- **Redirects are not followed.** A channel whose server answers with a
  redirect keeps its alerts queued and shows the reason; set the URL it
  redirects to.
- **Private and loopback addresses are allowed**, because Alertmanager, an
  internal webhook or an SMTP relay usually live there.

A destination that is refused keeps the channel's alerts queued with the
reason (shown as **Failing** in the console), so nothing is lost when you fix
it. Saving a console channel with a refused destination fails with the same
reason.

### Limiting console channels to some hosts

An admin can point a console channel at any host Heimdall reaches, which
includes internal services. To limit that, list the allowed destinations in
`heimdall.yaml`:

```yaml
console_channels:
  allowed_hosts:
    - "*.slack.com"            # any subdomain, not slack.com itself
    - hooks.example.com        # this host only
    - alertmanager.monitoring.svc
    - 10.20.0.0/16             # any address in the network
```

When the list is set, a console channel may only send to a host matching an
entry by name, or resolving to an address in a listed network. Channels in
`heimdall.yaml` are not limited by it. The list can only be set in the config
file, not in the console, because it limits what console admins can reach.

If Heimdall sends through a proxy (`HTTPS_PROXY`), the proxy connects to the
destination: the checks above still apply to the URL's host and the
addresses it resolves to on the Heimdall side.

## Troubleshooting

Watch `heimdall_outbox_pending` (messages waiting) and
`heimdall_notify_failures_total{channel_type}` (messages a channel rejected).
The logs name the channel and its type for every failed send, and warn once
when a channel's variable is not set. See [Metrics](/heimdall/reference/metrics/).

### Orphaned messages

Queued messages belong to a channel name and type. If you remove a channel,
rename it, or change its `type`, its unsent messages are never sent, and
Heimdall logs one warning per name and type naming them ("outbox has unsent
… alerts for channel `X`, which is no longer configured"). Either restore the
channel in `heimdall.yaml` (recreating it in the console discards them instead),
or clear them in the database:

```sql
-- See what is stuck.
SELECT route, channel_type, count(*) FROM outbox
WHERE sent_at IS NULL GROUP BY 1, 2;

-- Drop the unsent messages of a channel that is gone.
DELETE FROM outbox
WHERE sent_at IS NULL AND route = 'old-name' AND channel_type = 'slack';
```

Sent rows are removed after `retention.outbox_days` as usual.
