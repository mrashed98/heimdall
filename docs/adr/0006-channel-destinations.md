# Channel destinations are checked at connect time

Admins can create alert channels in the console, so an admin can make Heimdall send HTTP requests and SMTP connections to any address it reaches, and the Test button reports the result. That is a server-side request forgery surface. Heimdall rarely runs where only outside hosts matter: Alertmanager, internal webhooks and SMTP relays usually live on private addresses, and Heimdall is open source and runs in Kubernetes, on Docker hosts and on cloud VMs alike. So private and loopback addresses stay allowed, and three rules apply instead. Link-local and cloud metadata addresses are refused for every channel, since no alert destination lives there and the metadata service is where cloud credentials are taken from. Redirects are never followed, so a public URL cannot bounce a request inward. And the check happens when connecting: each send resolves the host, drops refused addresses and connects only to the ones checked, so a DNS answer that changes between check and connect (rebinding) cannot get around it; email connects to the checked address and still verifies the server certificate against the host name. Operators who want more can set `console_channels.allowed_hosts`, which limits console channels only; it lives in the config file, not the console, because it limits what console admins can do. Rejected: allowing only public addresses (breaks the common internal destinations), checking only when a channel is saved (DNS can change afterwards), and a console-editable allowlist (the people it limits could change it). What remains: without an allowlist, an admin can still reach internal hosts, and the status code of a Test send tells them whether something answered there. Through an HTTP proxy, the proxy makes the connection, so only the URL host and its addresses as resolved by Heimdall are checked.
